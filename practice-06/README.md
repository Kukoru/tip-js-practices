## 3. Реализация

### 3.1. HTTP-клиент
Клиент поддерживает методы GET, POST, PATCH и DELETE. Для запросов с телом автоматически добавляется заголовок `Content-Type: application/json` и выполняется `JSON.stringify`. Ответ 204 (No Content) возвращает `null` без попытки парсинга JSON. Реализовано ограничение времени (`AbortSignal.timeout`) и внешняя отмена (`AbortController`).

### 3.2. Доменный API
В `task-api.js` реализованы операции: `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`, `createTask`, `updateTask`, `setTaskCompleted`, `deleteTask`, `resetDemoData`. Схема ответа проверяется до передачи данных в интерфейс (проверка типов полей, уникальности id, соответствия `meta.total` длине массива).

### 3.3. Состояния интерфейса
Реализованы состояния: 
- `loading` (идет запрос, список скрыт, `aria-busy="true"`)
- `ready` (список получен, карточки отрисованы)
- `empty` (запрос успешен, но результатов нет — показывается сообщение)
- `error` (ошибка сети или сервера, показывается сообщение и кнопка «Повторить загрузку»).
При повторной загрузке состояние снова меняется на `loading`.

### 3.4. Изменение данных
После успешного POST, PATCH или DELETE приложение не изменяет локальный массив, а выполняет повторный GET-запрос с текущими фильтрами. Это гарантирует, что пользователь видит только подтвержденное сервером состояние (пессимистичный сценарий).

### 3.5. Защита от устаревшего ответа
При смене фильтра или повторной загрузке предыдущий запрос отменяется через `AbortController`. Дополнительно каждому запуску присваивается порядковый номер (`seq`), и результат применяется только в том случае, если номер завершившегося запроса совпадает с последним. Отмена не показывается пользователю как ошибка.

## 4. Индивидуальный вариант

**Начальный фильтр:** `{ completed: false }`
**Индивидуальный сценарий:** После загрузки списка невыполненных задач, задача `id = 4` отмечается выполненной. На сервер уходит `PATCH`, затем выполняется повторный `GET` с фильтром `completed=false`. Задача `id = 4` исчезает из списка, так как она больше не соответствует фильтру.

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**
   Потому что `fetch` отклоняет Promise только при сетевых сбоях. Ответ 404 — это успешно полученный HTTP-ответ от сервера (сервер доступен, но ресурс не найден).
2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?**
   Ответ 204 означает "No Content" (нет тела). Попытка распарсить пустую строку как JSON вызовет ошибку `SyntaxError`.
3. **Чем состояние `empty` отличается от `error`?**
   `empty` — это успешный запрос, который вернул 0 результатов (например, из-за фильтра). `error` — это сбой сети или сервера, который не позволил получить данные.
4. **Зачем отменять предыдущий запрос при смене фильтров?**
   Чтобы избежать "гонки запросов", когда старый (медленный) запрос завершается позже нового и перезаписывает интерфейс устаревшими данными.
5. **Почему после мутации список повторно запрашивается у API?**
   Чтобы интерфейс отображал только те данные, которые реально сохранены на сервере (сервер — единственный источник истины).

## 7. Дополнительное задание

**Выбранный вариант:** Debounce поиска (задержка 400 мс).

**Правила поведения:** При вводе текста в поле поиска (`#filter-query`) форма не отправляется сразу. Запускается таймер на 400 мс. Если пользователь продолжает печатать, таймер сбрасывается. Как только ввод прекращается на 400 мс, форма отправляется автоматически (`requestSubmit`), вызывая новый серверный запрос. Это снижает нагрузку на сервер и исключает отправку запросов на каждое нажатие клавиши.

**Проверки:**
1. Быстрый ввод текста -> запросы не отправляются, пока не пройдет 400 мс.
2. Ввод текста и пауза -> отправляется один запрос с полным введенным текстом.
3. Очистка поля -> автоматически применяется сброс фильтров.
