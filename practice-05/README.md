Рабочая папка: `practice-05` внутри личного репозитория.

Проверка готового API:

```bash
npm run check:api
```

Полный набор после реализации клиента:

```bash
npm test
```

Для ручного сценария необходимы два терминала.

Терминал 1:

```bash
npm start
```

Терминал 2:

```bash
npm run example:fetch
npm run client
```

Адрес API по умолчанию:

```text
http://127.0.0.1:5505/api
```

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Учебный локальный HTTP API (готовый). |
| `src/api-client.js` | Общий транспорт: URL, fetch, проверка статусов и JSON, ApiError. |
| `src/task-api.js` | Предметный API: маршруты `/tasks`, `/categories`, проверка схемы. |
| `src/variant.js` | Номер варианта и объект фильтров. |
| `src/main.js` | Контрольный сценарий в терминале, вывод результатов. |

`fetchFn` передаётся в `createApiClient` для подмены сети в тестах. HTTP-ошибки проверяются отдельно от сетевых, так как `fetch` не отклоняет Promise при 4xx и 5xx. JSON проверяется по контракту, так как синтаксически верный JSON может содержать неверную структуру.

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id `[4, 13, 34]` |

| `getCategories()` | 3 категории (Учёба, Проект, Организация) |
| `loadInitialData(...)` | `{ tasks, categories, meta }` |

Проверяется: положительный целый id, строка title от 1 до 100, boolean completed, допустимый priority, положительный categoryId, уникальность id и соответствие meta.total длине массива.

## Отладка

Точки останова установлены до `fetch`, после получения `Response`, перед `response.json()` и в обработчике `catch`. Для успешного запроса зафиксирован статус `200` и `Content-Type: application/json`. Для ошибочного — статус `404`, `kind: "http"`, `code: "TASK_NOT_FOUND"`.

## Дополнительное задание

**Выбранный вариант:** Вариант А (частичный результат через `Promise.allSettled`).

Реализован метод `loadInitialDataSettled`, который независимо запрашивает задачи и категории. Если один из запросов завершается ошибкой, результат другого сохраняется, а информация об ошибке передается в полях `tasksError` или `categoriesError`.

**Проверки:**
1. Успех обоих запросов -> возвращаются и задачи, и категории, ошибок нет.
2. Ошибка задач при доступных категориях -> `tasks: []`, `categories: [...]`, `tasksError` содержит объект `ApiError`.
3. Ошибка категорий при доступных задачах -> `tasks: [...]`, `categories: []`, `categoriesError` содержит объект `ApiError`.

## Вывод

В ходе работы освоены асинхронные операции, `fetch`, `async/await`, `Promise.all`, `AbortController` и `AbortSignal.timeout`. Реализован общий HTTP-клиент с разными типами ошибок (`http`, `network`, `invalid-response`, `timeout`, `aborted`) и предметный API задач с проверкой схемы. Ошибки HTTP (4xx, 5xx) отличаются от сетевых (нет связи), неверного ответа (не JSON) и отмены.
